title: GitHub Actions
description: CI/CD setup for changeset checking and automated releases.

changesetter ships composite GitHub Actions for checking changesets on PRs and running releases on merge to main.

## Versions

The actions are versioned separately from the CLI, with the tags GitHub recommends for actions:

| Ref | What you get |
|---|---|
| `@v1` | The latest v1.x release. Moved forward on every compatible release, so you get fixes without editing your workflow. |
| `@v1.1.0` | That release's action code. The tag never moves. |
| `@<commit sha>` | The same, pinned by commit. |

The check and release actions install the CLI through `actions/install@v1`, so that step follows `v1` even when you pin a tag or SHA. A change that breaks inputs, outputs or required permissions ships as `v2`, so `@v1` will not break your workflow. Release notes from v1.1.0 on are on the [releases page](https://github.com/saturate/changesetter/releases) under the `v1.x.y` tags. The CLI's own releases are tagged `changesetter@v<version>`, and the actions always install the latest CLI unless you pin `version`.

## Changeset check

Runs `changesetter check` on pull requests and posts a comment with the result. When the check passes, the comment has a collapsed section listing each changeset the PR adds, with its bumps and text.

```yaml
# .github/workflows/changeset-check.yml
name: Changeset Check
on:
  pull_request:
    types: [opened, synchronize, reopened]

permissions:
  contents: read
  pull-requests: write

jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0
      - uses: saturate/changesetter/actions/check@v1
        with:
          comment: true
```

### Inputs

| Input | Default | Description |
|---|---|---|
| `base` | Auto-detect from PR | Base branch to compare against |
| `comment` | `true` | Post/update a PR comment with the changeset summary |
| `version` | `latest` | changesetter version to install, or `none` to use a `changesetter` already on `PATH` |

The comment is updated on subsequent pushes rather than creating duplicates. It uses an HTML marker (`<!-- changesetter-check -->`) to find the existing bot comment. If the token can't write to the PR (a pull request from a fork, or no `pull-requests: write`), the job logs a warning instead of the comment, and the check still passes or fails. A changeset that can't be parsed fails the check, and the comment shows the error.

Requires changesetter 0.5.0 or newer (`changesetter check --output json`). The default `version: latest` covers this.

`fetch-depth: 0` is required for the `--base` diff to work.

## Direct release

Runs `changesetter release` on push to main, creates tags and GitHub Releases.

```yaml
# .github/workflows/release.yml
name: Release
on:
  push:
    branches: [main]

jobs:
  release:
    runs-on: ubuntu-latest
    permissions:
      contents: write
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0
      - uses: saturate/changesetter/actions/release@v1
        env:
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
```

When changesets are pending, the action bumps versions, updates changelogs, commits, tags, pushes, and creates GitHub Releases with the changelog as the body.

When no changesets are pending, the action does nothing.

### Inputs

| Input | Default | Description |
|---|---|---|
| `github-release` | `true` | Create GitHub Releases |
| `draft` | `false` | Create releases as drafts |
| `version-pr` | `false` | Use version-PR mode instead of direct release |
| `version-pr-title` | `"Version Packages"` | Title for the version PR |
| `version` | `latest` | changesetter version to install |

### Outputs

| Output | Description |
|---|---|
| `released` | `true` if releases were created |
| `releases` | JSON array of `{name, version, tag, changelog}` |
| `version-pr` | URL of the version PR (version-PR mode only) |

## Version-PR mode

Instead of releasing directly on merge, create a "Version Packages" PR that batches all pending changesets. Merging that PR triggers the actual release.

```yaml
name: Release
on:
  push:
    branches: [main]

concurrency:
  group: changesetter-release
  cancel-in-progress: false

jobs:
  release:
    runs-on: ubuntu-latest
    permissions:
      contents: write
      pull-requests: write
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0
      - uses: saturate/changesetter/actions/release@v1
        with:
          version-pr: true
        env:
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
```

The flow:
1. Push to main with pending changesets: creates/updates a PR on `changesetter/version-packages` branch with label `changesetter:version`
2. Push to main whose HEAD is the merge commit of a version PR: releases every package whose version the PR changed. Each gets a tag in your configured tag format, at the merge commit, plus a GitHub Release with that version's changelog section as notes. Pre-release versions become pre-releases.
3. Any other push without pending changesets: does nothing

A version PR merge that also brings in changesets merged while it was open does both: it releases, then opens a new version PR for those changesets.

Releasing is safe to repeat. Tags and GitHub Releases that already exist are left alone, and `released` is only `true` for what the run actually created. If the run for a merge was cancelled or failed partway, the next push to main finishes the release of the last merged version PR.

Requirements:
- `actions/checkout` with `fetch-depth: 0`. The action reads the merge's parent commit and the existing tags.
- changesetter 0.4.0 or newer (`changesetter status --output json`). The default `version: latest` covers this.
- `pull-requests: write` to create PRs.

The `concurrency` group prevents races when multiple pushes arrive in quick succession. `cancel-in-progress: false` keeps the release run for a merge from being cancelled by the next push; if one is cancelled anyway, the next push picks it up.

## Permissions

| Permission | When needed |
|---|---|
| `contents: write` | Always (for commits, tags, releases) |
| `pull-requests: write` | Version-PR mode only |

## Install action

The check and release actions use the install action internally. If you need the binary in a custom step:

```yaml
- uses: saturate/changesetter/actions/install@v1
  with:
    version: latest
```

This downloads the prebuilt binary from GitHub Releases and adds it to PATH. Results are cached by version and platform.

| Input | Default | Description |
|---|---|---|
| `version` | `latest` | `latest`, or a version such as `0.3.3`, `v0.3.3` or `changesetter@v0.3.3`. `latest` is the newest stable release that has a binary for the runner. |
| `cache` | `true` | Cache the binary between runs. Set to `false` to always download. |
