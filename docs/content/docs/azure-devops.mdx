changesetter works with Azure Pipelines the same way it works anywhere: download the binary, run the commands. These pipeline templates cover the common patterns.

## Install changesetter

Download a pinned version, verify it against the release's `SHA256SUMS`, and put it on the `PATH` for later steps:

```yaml
- script: |
    set -euo pipefail
    VERSION=0.9.0
    case "$(uname -m)" in
      x86_64) TARGET=x86_64-unknown-linux-gnu ;;
      aarch64|arm64) TARGET=aarch64-unknown-linux-gnu ;;
      *) echo "Unsupported architecture $(uname -m)" >&2; exit 1 ;;
    esac
    BASE="https://github.com/saturate/changesetter/releases/download/changesetter%40v${VERSION}"
    cd "$(Agent.TempDirectory)"
    curl -fsSLO "${BASE}/changesetter-${TARGET}.tar.gz"
    curl -fsSLO "${BASE}/SHA256SUMS"
    grep " changesetter-${TARGET}.tar.gz\$" SHA256SUMS | sha256sum --check -
    mkdir -p "$(Pipeline.Workspace)/tools"
    tar xzf "changesetter-${TARGET}.tar.gz" -C "$(Pipeline.Workspace)/tools"
    echo "##vso[task.prependpath]$(Pipeline.Workspace)/tools"
  displayName: Install changesetter
```

The archive is downloaded outside the repository, so it can't end up in a commit. `SHA256SUMS` is published from 0.9.0 on; see [Verify a download](/#verify-a-download) for the build provenance check. To follow the newest release instead of pinning, use `https://github.com/saturate/changesetter/releases/latest/download` as `BASE`.

## Changeset check on PRs

Verify that every PR includes a changeset. Runs on pull request triggers only.

```yaml
trigger: none

pr:
  branches:
    include:
      - main

pool:
  vmImage: ubuntu-latest

steps:
  - checkout: self
    fetchDepth: 0

  - script: |
      set -euo pipefail
      VERSION=0.9.0
      TARGET=x86_64-unknown-linux-gnu
      BASE="https://github.com/saturate/changesetter/releases/download/changesetter%40v${VERSION}"
      cd "$(Agent.TempDirectory)"
      curl -fsSLO "${BASE}/changesetter-${TARGET}.tar.gz"
      curl -fsSLO "${BASE}/SHA256SUMS"
      grep " changesetter-${TARGET}.tar.gz\$" SHA256SUMS | sha256sum --check -
      mkdir -p "$(Pipeline.Workspace)/tools"
      tar xzf "changesetter-${TARGET}.tar.gz" -C "$(Pipeline.Workspace)/tools"
      echo "##vso[task.prependpath]$(Pipeline.Workspace)/tools"
    displayName: Install changesetter

  - script: |
      changesetter check --base origin/$(System.PullRequest.TargetBranch)
    displayName: Check changeset
```

### PR comments

To post a comment on the PR with the changeset summary, add a step after the check:

```yaml
  - script: |
      OUTPUT=$(changesetter check --base origin/$(System.PullRequest.TargetBranch) 2>&1) || true
      EXIT_CODE=$?

      if [ "$EXIT_CODE" -eq 0 ]; then
        COMMENT="### Changeset Check: Passed\n\n\`\`\`\n${OUTPUT}\n\`\`\`"
      else
        COMMENT="### Changeset Check: Missing\n\nNo changeset found. Run \`changesetter add\` to create one."
      fi

      PR_ID=$(System.PullRequest.PullRequestId)
      ORG_URL=$(System.CollectionUri)
      PROJECT=$(System.TeamProject)
      REPO=$(Build.Repository.Name)

      curl -s -X POST \
        "${ORG_URL}${PROJECT}/_apis/git/repositories/${REPO}/pullRequests/${PR_ID}/threads?api-version=7.1" \
        -H "Authorization: Bearer $(System.AccessToken)" \
        -H "Content-Type: application/json" \
        -d "{\"comments\":[{\"content\":\"${COMMENT}\",\"commentType\":1}],\"status\":1}"
    displayName: Post PR comment
    condition: always()
    env:
      SYSTEM_ACCESSTOKEN: $(System.AccessToken)
```

## Release on merge to main

### Direct release

Run `changesetter release` on every push to main. The pipeline bumps versions, updates the changelog, commits, tags, and pushes.

```yaml
trigger:
  branches:
    include:
      - main

pr: none

pool:
  vmImage: ubuntu-latest

steps:
  - checkout: self
    fetchDepth: 0
    persistCredentials: true

  - script: |
      set -euo pipefail
      VERSION=0.9.0
      TARGET=x86_64-unknown-linux-gnu
      BASE="https://github.com/saturate/changesetter/releases/download/changesetter%40v${VERSION}"
      cd "$(Agent.TempDirectory)"
      curl -fsSLO "${BASE}/changesetter-${TARGET}.tar.gz"
      curl -fsSLO "${BASE}/SHA256SUMS"
      grep " changesetter-${TARGET}.tar.gz\$" SHA256SUMS | sha256sum --check -
      mkdir -p "$(Pipeline.Workspace)/tools"
      tar xzf "changesetter-${TARGET}.tar.gz" -C "$(Pipeline.Workspace)/tools"
      echo "##vso[task.prependpath]$(Pipeline.Workspace)/tools"
    displayName: Install changesetter

  - script: |
      git config user.name "Azure Pipelines"
      git config user.email "pipelines@dev.azure.com"
    displayName: Configure git

  - script: |
      OUTPUT=$(changesetter release --output json 2>&1) || EXIT_CODE=$?

      if [ "${EXIT_CODE:-0}" -ne 0 ]; then
        echo "changesetter release failed"
        exit 0
      fi

      if [ -z "$OUTPUT" ] || ! echo "$OUTPUT" | jq -e '.releases' > /dev/null 2>&1; then
        echo "No releases to create."
        exit 0
      fi

      echo "$OUTPUT" | jq .
      git push --atomic origin main --follow-tags
    displayName: Release
```

Azure DevOps doesn't have a "GitHub Releases" equivalent. The release is the git tag itself. Use Azure Artifacts or your own distribution mechanism for binaries.

### Version-PR pattern

Instead of releasing on every merge, create a PR that batches pending changesets. Merging that PR triggers the release.

Only the build for the version PR's merge commit releases, so leave `batch` off in the trigger. With `batch: true`, a push that lands while that build is queued folds the merge commit into a later build, and the release never happens.

```yaml
trigger:
  branches:
    include:
      - main

pr: none

pool:
  vmImage: ubuntu-latest

steps:
  - checkout: self
    fetchDepth: 0
    persistCredentials: true

  - script: |
      set -euo pipefail
      VERSION=0.9.0
      TARGET=x86_64-unknown-linux-gnu
      BASE="https://github.com/saturate/changesetter/releases/download/changesetter%40v${VERSION}"
      cd "$(Agent.TempDirectory)"
      curl -fsSLO "${BASE}/changesetter-${TARGET}.tar.gz"
      curl -fsSLO "${BASE}/SHA256SUMS"
      grep " changesetter-${TARGET}.tar.gz\$" SHA256SUMS | sha256sum --check -
      mkdir -p "$(Pipeline.Workspace)/tools"
      tar xzf "changesetter-${TARGET}.tar.gz" -C "$(Pipeline.Workspace)/tools"
      echo "##vso[task.prependpath]$(Pipeline.Workspace)/tools"
    displayName: Install changesetter

  - script: |
      git config user.name "Azure Pipelines"
      git config user.email "pipelines@dev.azure.com"
    displayName: Configure git

  - script: |
      set -eo pipefail
      BRANCH="changesetter/version-packages"
      ORG_URL=$(System.CollectionUri)
      PROJECT=$(System.TeamProject)
      REPO=$(Build.Repository.Name)

      # Release only when this build's commit is a completed version PR's merge
      # commit. Matching the newest completed version PR instead would make
      # every later push look like a release, and an active PR's
      # lastMergeCommit is the test merge its PR validation builds run on.
      # curl -f fails the step on API errors so a bad token does not quietly
      # skip the release.
      COMMIT=$(Build.SourceVersion)
      MERGED_PR=$(curl -sSf -X POST \
        "${ORG_URL}${PROJECT}/_apis/git/repositories/${REPO}/pullrequestquery?api-version=7.1" \
        -H "Authorization: Bearer $(System.AccessToken)" \
        -H "Content-Type: application/json" \
        -d "{\"queries\":[{\"type\":\"lastMergeCommit\",\"items\":[\"${COMMIT}\"]}]}" \
        | jq -er --arg sha "$COMMIT" --arg ref "refs/heads/${BRANCH}" \
          '[(.results // error("no results in response"))[0][$sha][]? | select(.sourceRefName == $ref and .status == "completed" and .lastMergeCommit.commitId == $sha) | .pullRequestId] | first // ""')

      if [ -n "$MERGED_PR" ]; then
        echo "Commit is the merge of version PR #${MERGED_PR}, tagging"
        # Tags every package whose version the merge changed, in the
        # configured tag format and minus [tag] skip, and pushes them in one
        # atomic push. It fails on a version collision: a tag for one of
        # those versions already on origin at another commit.
        changesetter tag --since "${COMMIT}^1" --push
      fi

      # Changesets merged while the version PR was open still need a version
      # PR, even right after a release.
      # Nested dirs count, README.md doesn't, matching changesetter itself.
      # -print -quit rather than `| grep -q`: with pipefail, a long listing
      # makes find die of SIGPIPE and the check would read "none pending".
      if [ -z "$(find .changeset -type f -name '*.md' ! -name README.md -print -quit 2>/dev/null)" ]; then
        echo "No pending changesets"
        exit 0
      fi

      # Compute status
      STATUS=$(changesetter status 2>&1 || true)

      # Create version branch and apply changes
      git checkout -B "$BRANCH"
      changesetter version --no-commit
      git add -A
      git commit -m "chore: version packages" --allow-empty
      git push origin "$BRANCH" --force
      git checkout -

      # Create or update PR via Azure DevOps REST API
      PR_BODY=$(printf 'This PR was opened by changesetter. Merging it will release the following packages.\n\n```\n%s\n```' "$STATUS")

      # Check for existing PR
      EXISTING=$(curl -sSf \
        "${ORG_URL}${PROJECT}/_apis/git/repositories/${REPO}/pullrequests?searchCriteria.sourceRefName=refs/heads/${BRANCH}&searchCriteria.status=active&api-version=7.1" \
        -H "Authorization: Bearer $(System.AccessToken)" \
        | jq -r '.value[0].pullRequestId // empty')

      if [ -n "$EXISTING" ]; then
        # jq builds the JSON so quotes and newlines in the status stay valid.
        jq -n --arg d "$PR_BODY" '{description: $d}' | curl -sSf -o /dev/null -X PATCH \
          "${ORG_URL}${PROJECT}/_apis/git/repositories/${REPO}/pullrequests/${EXISTING}?api-version=7.1" \
          -H "Authorization: Bearer $(System.AccessToken)" \
          -H "Content-Type: application/json" \
          --data-binary @-
        echo "Updated PR #${EXISTING}"
      else
        jq -n --arg src "refs/heads/${BRANCH}" --arg d "$PR_BODY" \
          '{sourceRefName: $src, targetRefName: "refs/heads/main", title: "Next Release", description: $d}' \
          | curl -sSf -o /dev/null -X POST \
          "${ORG_URL}${PROJECT}/_apis/git/repositories/${REPO}/pullrequests?api-version=7.1" \
          -H "Authorization: Bearer $(System.AccessToken)" \
          -H "Content-Type: application/json" \
          --data-binary @-
        echo "Created version PR"
      fi
    displayName: Create version PR or release
    env:
      SYSTEM_ACCESSTOKEN: $(System.AccessToken)
```

## Azure Pipelines extension

For a more integrated experience, changesetter provides an Azure Pipelines extension with custom tasks for checking and releasing. See `extensions/azure-pipelines/` in the changesetter repository.

The extension wraps the same CLI commands with native Azure DevOps integration: PR comment threads, work item linking, and pipeline variables.

In version-PR mode, the `ChangsetterRelease` task releases only when the commit being built (`Build.SourceVersion`) is the merge commit of a completed `changesetter/version-packages` PR. It runs `changesetter tag --since <merge target> --push`, which tags every package whose version the merge changed (`v<version>` in a single-package repo, `<name>@v<version>` in a monorepo, or your `[tag] format`), leaves out packages matched by `[tag] skip`, and pushes the new tags to origin in one atomic push. A tag that already exists on origin at the same commit is skipped and still reported, so re-running a failed release build is safe. If one exists at a different commit, the task fails with a version collision and pushes no tags. The `released`, `releases` (`[{ name, version, tag }]`) and `version` (the first release's) output variables cover the tagged packages. If changesets were merged while the version PR was open, the same run then opens or updates a new version PR for them. A failed Azure DevOps API call fails the task instead of skipping the release, and so does a failing `changesetter version`, so a half-bumped tree never becomes a version PR. The task needs a CLI with `changesetter tag` (0.9.0 or newer); its default `version: latest` installs one.

## Permissions

The Build Service identity needs the following permissions on the repository:

| Permission | Required for |
|---|---|
| Contribute | Pushing release commits |
| Create tag | Creating version tags |
| Contribute to pull requests | Posting PR comments, creating version PRs |
| Create branch | Creating the `changesetter/version-packages` branch |

Set these under **Project Settings > Repositories > Security**. Find your build service account (usually `{Project Name} Build Service ({org})`) and grant the permissions listed above.

If using `persistCredentials: true` in the checkout step, the pipeline's access token inherits permissions from the Build Service identity. No extra token management needed for most setups.
