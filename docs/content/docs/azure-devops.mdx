changesetter works with Azure Pipelines the same way it works anywhere: download the binary, run the commands. These pipeline templates cover the common patterns.

## Install changesetter

Download a pinned version, verify it against the release's `SHA256SUMS`, and put it on the `PATH` for later steps:

```yaml
- script: |
    set -euo pipefail
    VERSION=0.9.0
    case "$(uname -m)" in
      x86_64) TARGET=x86_64-unknown-linux-gnu ;;
      aarch64|arm64) TARGET=aarch64-unknown-linux-gnu ;;
      *) echo "Unsupported architecture $(uname -m)" >&2; exit 1 ;;
    esac
    BASE="https://github.com/saturate/changesetter/releases/download/changesetter%40v${VERSION}"
    cd "$(Agent.TempDirectory)"
    curl -fsSLO "${BASE}/changesetter-${TARGET}.tar.gz"
    curl -fsSLO "${BASE}/SHA256SUMS"
    grep " changesetter-${TARGET}.tar.gz\$" SHA256SUMS | sha256sum --check -
    mkdir -p "$(Pipeline.Workspace)/tools"
    tar xzf "changesetter-${TARGET}.tar.gz" -C "$(Pipeline.Workspace)/tools"
    echo "##vso[task.prependpath]$(Pipeline.Workspace)/tools"
  displayName: Install changesetter
```

The archive is downloaded outside the repository, so it can't end up in a commit. `version-pr` reads the agent's certificate store for its HTTPS calls, so a container job on a minimal image needs the `ca-certificates` package. `SHA256SUMS` is published from 0.9.0 on; see [Verify a download](/#verify-a-download) for the build provenance check. To follow the newest release instead of pinning, use `https://github.com/saturate/changesetter/releases/latest/download` as `BASE`.

## Changeset check on PRs

Verify that every PR includes a changeset. Runs on pull request triggers only.

```yaml
trigger: none

pr:
  branches:
    include:
      - main

pool:
  vmImage: ubuntu-latest

steps:
  - checkout: self
    fetchDepth: 0

  - script: |
      set -euo pipefail
      VERSION=0.9.0
      TARGET=x86_64-unknown-linux-gnu
      BASE="https://github.com/saturate/changesetter/releases/download/changesetter%40v${VERSION}"
      cd "$(Agent.TempDirectory)"
      curl -fsSLO "${BASE}/changesetter-${TARGET}.tar.gz"
      curl -fsSLO "${BASE}/SHA256SUMS"
      grep " changesetter-${TARGET}.tar.gz\$" SHA256SUMS | sha256sum --check -
      mkdir -p "$(Pipeline.Workspace)/tools"
      tar xzf "changesetter-${TARGET}.tar.gz" -C "$(Pipeline.Workspace)/tools"
      echo "##vso[task.prependpath]$(Pipeline.Workspace)/tools"
    displayName: Install changesetter

  - script: |
      changesetter check --base origin/$(System.PullRequest.TargetBranch)
    displayName: Check changeset
```

### PR comments

To post a comment on the PR with the changeset summary, add a step after the check:

```yaml
  - script: |
      OUTPUT=$(changesetter check --base origin/$(System.PullRequest.TargetBranch) 2>&1) || true
      EXIT_CODE=$?

      if [ "$EXIT_CODE" -eq 0 ]; then
        COMMENT="### Changeset Check: Passed\n\n\`\`\`\n${OUTPUT}\n\`\`\`"
      else
        COMMENT="### Changeset Check: Missing\n\nNo changeset found. Run \`changesetter add\` to create one."
      fi

      PR_ID=$(System.PullRequest.PullRequestId)
      ORG_URL=$(System.CollectionUri)
      PROJECT=$(System.TeamProject)
      REPO=$(Build.Repository.Name)

      curl -s -X POST \
        "${ORG_URL}${PROJECT}/_apis/git/repositories/${REPO}/pullRequests/${PR_ID}/threads?api-version=7.1" \
        -H "Authorization: Bearer $(System.AccessToken)" \
        -H "Content-Type: application/json" \
        -d "{\"comments\":[{\"content\":\"${COMMENT}\",\"commentType\":1}],\"status\":1}"
    displayName: Post PR comment
    condition: always()
    env:
      SYSTEM_ACCESSTOKEN: $(System.AccessToken)
```

## Release on merge to main

### Direct release

Run `changesetter release` on every push to main. The pipeline bumps versions, updates the changelog, commits, tags, and pushes.

```yaml
trigger:
  branches:
    include:
      - main

pr: none

pool:
  vmImage: ubuntu-latest

steps:
  - checkout: self
    fetchDepth: 0
    persistCredentials: true

  - script: |
      set -euo pipefail
      VERSION=0.9.0
      TARGET=x86_64-unknown-linux-gnu
      BASE="https://github.com/saturate/changesetter/releases/download/changesetter%40v${VERSION}"
      cd "$(Agent.TempDirectory)"
      curl -fsSLO "${BASE}/changesetter-${TARGET}.tar.gz"
      curl -fsSLO "${BASE}/SHA256SUMS"
      grep " changesetter-${TARGET}.tar.gz\$" SHA256SUMS | sha256sum --check -
      mkdir -p "$(Pipeline.Workspace)/tools"
      tar xzf "changesetter-${TARGET}.tar.gz" -C "$(Pipeline.Workspace)/tools"
      echo "##vso[task.prependpath]$(Pipeline.Workspace)/tools"
    displayName: Install changesetter

  - script: |
      git config user.name "Azure Pipelines"
      git config user.email "pipelines@dev.azure.com"
    displayName: Configure git

  - script: |
      OUTPUT=$(changesetter release --output json 2>&1) || EXIT_CODE=$?

      if [ "${EXIT_CODE:-0}" -ne 0 ]; then
        echo "changesetter release failed"
        exit 0
      fi

      if [ -z "$OUTPUT" ] || ! echo "$OUTPUT" | jq -e '.releases' > /dev/null 2>&1; then
        echo "No releases to create."
        exit 0
      fi

      echo "$OUTPUT" | jq .
      git push --atomic origin main --follow-tags
    displayName: Release
```

Azure DevOps doesn't have a "GitHub Releases" equivalent. The release is the git tag itself. Use Azure Artifacts or your own distribution mechanism for binaries.

### Version-PR pattern

Instead of releasing on every merge, create a PR that batches pending changesets. Merging that PR triggers the release.

Only the build for the version PR's merge commit releases, so leave `batch` off in the trigger. With `batch: true`, a push that lands while that build is queued folds the merge commit into a later build, and the release never happens.

```yaml
trigger:
  branches:
    include:
      - main

pr: none

pool:
  vmImage: ubuntu-latest

steps:
  - checkout: self
    fetchDepth: 0
    persistCredentials: true

  - script: |
      set -euo pipefail
      VERSION=0.9.0
      TARGET=x86_64-unknown-linux-gnu
      BASE="https://github.com/saturate/changesetter/releases/download/changesetter%40v${VERSION}"
      cd "$(Agent.TempDirectory)"
      curl -fsSLO "${BASE}/changesetter-${TARGET}.tar.gz"
      curl -fsSLO "${BASE}/SHA256SUMS"
      grep " changesetter-${TARGET}.tar.gz\$" SHA256SUMS | sha256sum --check -
      mkdir -p "$(Pipeline.Workspace)/tools"
      tar xzf "changesetter-${TARGET}.tar.gz" -C "$(Pipeline.Workspace)/tools"
      echo "##vso[task.prependpath]$(Pipeline.Workspace)/tools"
    displayName: Install changesetter

  - script: changesetter version-pr --provider azure --title "Next Release"
    displayName: Tag the version PR merge, update the version PR
    env:
      SYSTEM_ACCESSTOKEN: $(System.AccessToken)
```

`changesetter version-pr` does the whole loop, reading `SYSTEM_ACCESSTOKEN`, `SYSTEM_COLLECTIONURI`, `SYSTEM_TEAMPROJECT`, `BUILD_REPOSITORY_ID` and `BUILD_SOURCEVERSION` from the job. Only the token has to be mapped in with `env:`; Azure Pipelines doesn't expose it otherwise.

1. It asks Azure DevOps whether the commit being built is the merge commit of a completed `changesetter/version-packages` PR. It matches by merge commit, because the newest completed version PR stays completed forever and an active PR's merge commit is the test merge its PR validation builds run on. A failed API call fails the step instead of looking like "not a version PR".
2. If it is, it runs [`tag --since <merge target> --push`](/cli#changesetter-tag): every package whose version the merge changed gets its tag, minus `[tag] skip`, pushed in one atomic push. The merge target comes from the PR, and is fetched when the checkout is shallow.
3. If changesets are pending (also right after a release, since changesets can land while the version PR is open), it runs `version` in a temporary worktree of HEAD, commits the result, force-pushes it as `changesetter/version-packages` and creates or updates the version PR. The build's own checkout isn't touched, so uncommitted changes and downloaded files in it never reach the version PR, and a failed bump leaves it as it was. `post_bump` hooks run in that worktree, which has no `node_modules` or other ignored files, so a hook needs to install what it uses (`pnpm install --lockfile-only` works). They run without `SYSTEM_ACCESSTOKEN`, and their output goes to the log. Git hooks don't run there. Only the version branch is pushed, so `main` stays protected.

The version PR's description is a changelog preview: one section per package with its version change and the entries as they go into its changelog, packages bumped only by a dependency cascade on one line each, and none-bump notes listed by title. Azure DevOps caps descriptions at 4000 characters, so whole sections are dropped from the end when needed and a note names the packages left out.

With `--output json` it prints `{"merged_pr", "commit", "recovered", "tags", "released", "version_pr"}`, where `tags` is the [`tag --output json`](/cli#changesetter-tag) list and `version_pr` is `{"id", "url", "created"}` or `null`. Options: `--title` (default `Version Packages`), `--base` for the branch the PR targets (default `main`), `--commit` to check another commit than the build's, and `--remote` (default `origin`). Without a git identity in the checkout, the version commit is authored as `changesetter`.

## Azure Pipelines extension

For a more integrated experience, changesetter provides an Azure Pipelines extension with custom tasks for checking and releasing. See `extensions/azure-pipelines/` in the changesetter repository.

The extension wraps the same CLI commands with native Azure DevOps integration: PR comment threads, work item linking, and pipeline variables.

In version-PR mode, the `ChangsetterRelease` task runs [`changesetter version-pr --provider azure`](#version-pr-pattern) with the pipeline's variables, so it behaves as described there. The `released`, `releases` (`[{ name, version, tag }]`) and `version` (the first release's) output variables cover the packages tagged for the merge; a tag that already exists on origin at that commit is still reported, so re-running a failed release build is safe and sets `released` again. That differs from the CLI's own `released` JSON list, which only has what the run created. `versionPrId` is the version PR it created or updated. The task needs changesetter 0.9.0 or newer; its default `version: latest` installs one.

## Permissions

The Build Service identity needs the following permissions on the repository:

| Permission | Required for |
|---|---|
| Contribute | Pushing release commits |
| Create tag | Creating version tags |
| Contribute to pull requests | Posting PR comments, creating version PRs |
| Create branch | Creating the `changesetter/version-packages` branch |

Set these under **Project Settings > Repositories > Security**. Find your build service account (usually `{Project Name} Build Service ({org})`) and grant the permissions listed above.

If using `persistCredentials: true` in the checkout step, the pipeline's access token inherits permissions from the Build Service identity. No extra token management needed for most setups.
